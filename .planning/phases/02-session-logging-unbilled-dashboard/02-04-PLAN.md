<objective>
Close the single BLOCKER gap from 02-VERIFICATION.md (CR-01, confirmed by 02-REVIEW.md): the Log Session / Edit Session dialog silently fails to auto-close on the 2nd+ consecutive successful save, breaking the tutor's primary real-world workflow of logging several sessions in one sitting and risking accidental duplicate rows from a confused re-click.

Root cause: both `addSessionAction` and `editSessionAction` in `lib/actions/sessions.ts` return the shared module-level constant `initialSessionActionState` on their success paths. `components/session-form-dialog.tsx` decides whether to auto-close via reference-inequality (`state !== prevState`). The first success differs from the dialog's own local `initialState` literal, so it closes; every subsequent success returns the exact same constant reference, so `state !== prevState` is false and the dialog stays open even though the DB write succeeded.

Fix: return a fresh `{ fieldErrors: null }` object literal on every success path so the reference always changes. Apply the identical fix to `lib/actions/students.ts` (`addStudentAction`/`editStudentAction`), which returns `initialStudentActionState` the same way and has the identical latent defect (same `state !== prevState` close logic in `components/student-form-dialog.tsx:55`).

Purpose: restore repeatable session logging/editing (SESS-01) without regressing any other verified Phase 2 behavior.
Output: two edited Server Action files; a human-verified back-to-back logging behavior.
</objective>
