# 07-01: Schema Foundation & Backend Mailer Setup

**Wave**: 1 (foundation — blocks Wave 2, 3, 4)

**Goal**: Add schema columns for Gmail credential storage, implement nodemailer transporter, and build the atomic `sendInvoiceViaGmail` helper + verification flow.

**Requirements**: BULK-01 (credential storage), BULK-03 (send helper), BULK-05 (verification)

## Tasks

    - `gmailVerified: boolean('gmail_verified').default(false)` — tracks if credential passed verification

### T2: Set up nodemailer transporter + encryption helper
- File: `lib/mailer.ts` (new)
  - Import `nodemailer`, `crypto` (built-in)
  - Implement `encryptAppPassword(plaintext: string): string`
    - Use Node's `crypto.scryptSync` to derive 32-byte key from `process.env.ENCRYPTION_KEY`
    - Generate random 16-byte IV
    - AES-256-CBC encrypt the app password
    - Return `"${iv.toString('hex')}:${encrypted}"`
  - Implement `decryptAppPassword(ciphertext: string): string`
    - Split on `:` to recover IV and encrypted text
    - Decrypt using same key + IV
    - Return plaintext app password
  - Implement `createGmailTransporter(appPassword: string): nodemailer.Transporter`
    - Hardcode `host: 'smtp.gmail.com'`, `port: 587`, `secure: false` (TLS)
    - Return `nodemailer.createTransport({ host, port, secure, auth: { user: gmailUser, pass: appPassword } })`
    - Note: `gmailUser` will be passed as parameter or from settings.userEmail (use a new settings.userEmail field? or pass as param?)

**Decision Point**: Should Gmail user email be stored in settings? For now, require it as a parameter to `createGmailTransporter`, or store it separately. Recommend storing as `settings.gmailUserEmail` to avoid confusion.

**Acceptance**: `lib/mailer.ts` exports `encryptAppPassword`, `decryptAppPassword`, `createGmailTransporter`. Can be imported without errors.

### T3: Implement `sendInvoiceViaGmail` helper
- File: `lib/mailer.ts` (extends T2)
  - Signature: `async function sendInvoiceViaGmail(opts: { invoice: InvoiceRow, gmailAppPassword: string, gmailUserEmail: string }): Promise<{ ok: boolean; error?: string }>`
  - Logic:
    1. Decrypt app password
    2. Create transporter via `createGmailTransporter`
    3. Send via `transporter.sendMail({ from: gmailUserEmail, to: invoice.parentEmail, subject: invoice.renderedSubject, text: invoice.renderedBody })`
    4. Catch errors: map specific error codes to user-friendly messages (EAUTH → "Credential invalid", ETIMEDOUT → "Network timeout", 454 → "Rate limited—try again later")
    5. Return `{ ok: true }` on success or `{ ok: false, error: "..." }` on failure
  - Do NOT catch top-level errors (caller handles logging/reporting)

**Acceptance**: Can call `sendInvoiceViaGmail` with a test invoice and valid credential; sends successfully or returns clear error.

### T4: Implement `updateGmailCredential` Server Action
- File: `lib/actions/settings.ts` (or new file `lib/actions/email.ts`)
  - Signature: `async function updateGmailCredential(appPassword: string, gmailUserEmail: string): Promise<{ ok: boolean; verified: boolean; error?: string }>`
  - Validation:
    - Reject if appPassword is not 16 characters (App Password format: `xxxx xxxx xxxx xxxx` after spaces removed)
    - Reject if gmailUserEmail is not a valid email
  - Logic:
    1. Encrypt the app password via `encryptAppPassword`
    2. Store encrypted password + email in `settings` table (update id=1 row)
    3. Test verification: call `createGmailTransporter` and attempt `transporter.verify()` (built-in nodemailer method)
    4. If verify succeeds: set `gmailVerified = true`, `gmailLastError = null`
    5. If verify fails: set `gmailVerified = false`, `gmailLastError = err.message` (store up to ~200 chars)
    6. Return `{ ok: true, verified: gmailVerified }` or `{ ok: false, error: "..." }` if exception
  - Revalidate `/settings` cache on success

**Acceptance**: After calling with valid Gmail App Password, `gmailVerified` is true and no error is stored.
