# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Greenfield note:** This is the first UI-SPEC for TutorInvoice. No design system, `components.json`, `tailwind.config.*`, or `src/` exists yet (repo contains only `CLAUDE.md` and `.planning/`). This document establishes the foundational visual language every later phase (2 and 3) inherits — treat every token below as the project baseline, not a phase-1-only choice.

**No interactive design session was available for this run** (subagent context, no user prompt channel). Every value below is either (a) pre-populated directly from a locked CONTEXT.md decision (cited by D-#), (b) pre-populated from RESEARCH.md's confirmed stack, or (c) a sensible, clearly-labeled default chosen per the objective's framing ("clean, minimal, appropriate for a single non-technical business owner using it on both phone and laptop"). Defaults are flagged `[DEFAULT]` so the checker/planner/user can override before execution.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps inside buttons, inline badge padding |
| sm | 8px | Compact spacing: table cell vertical padding, form field label-to-input gap |
| md | 16px | Default element spacing: form field-to-field gap, modal internal padding, table cell horizontal padding |
| lg | 24px | Section padding: page header-to-content gap, modal header-to-body gap |
| xl | 32px | Layout gaps: page top/bottom margin on desktop |
| 2xl | 48px | Major section breaks: not used this phase (single-surface page, no multi-section layout) |
| 3xl | 64px | Page-level spacing: not used this phase |

**Exceptions:**
- Touch targets on mobile: all interactive elements (buttons, row action icons, the password input's submit button) must be a minimum **44×44px** hit area even where the visual element is smaller — required because the app is explicitly used "on both phone and laptop" (objective) and D-14 calls out the add/edit modal must be mobile-friendly. Achieve via padding, not by shrinking the 8pt content box.
- Login screen password input + Unlock button: use `lg` (24px) vertical spacing around the single form group to give the lone input visual weight on an otherwise empty screen.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Exactly 2 weights declared (400, 600) and 4 sizes, per contract limits.

**Usage mapping for this phase's surfaces:**
- **Display (28/600/1.2):** Page title — "Students" on the roster page, "Archived Students" on the archived view.
- **Heading (20/600/1.2):** Modal titles ("Add Student" / "Edit Student"), archive-confirm dialog title ("Archive [Name]?"), login screen app name ("TutorInvoice").
- **Label (14/600/1.5):** Table column headers (Name / Rate / Parent Email), form field labels (Name / Hourly Rate / Parent Email), the login screen's "Password" label, inline validation error text (colored, not just weight — see Color).
- **Body (16/400/1.5):** Table cell values (student name, `$X.XX` rate, parent email), form input text, empty-state body copy, button labels, rate-limit/login error message text.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` (white) | Page background, modal/dialog background, card/table surface background. |
| Secondary (30%) | `#F4F4F5` (zinc-100) | Table header row background, alternating/hover table row background, login screen card background (distinguishing it from the page canvas behind it), disabled input background. |
| Accent (10%) | `#2563EB` (blue-600) | Reserved **exclusively** for: the "Add Student" primary CTA button, the login screen's "Unlock" button, the modal's primary Add Student / Save Changes button, focus rings on inputs, the active/selected state of the Students↔Archived tab link, and hyperlink-style text (none planned this phase, reserved for future use). |
| Destructive | `#DC2626` (red-600) | Reserved **exclusively** for: the Archive-confirm dialog's "Archive" button, inline field-validation error text (D-16: "Enter a name", "Rate must be a positive number", "Enter a valid email"), and the login screen's "Incorrect password." message. |

**Accent reserved for:** Add Student button · Unlock button · modal primary button · input focus rings · active tab indicator (Students/Archived). Nothing else may use the accent blue this phase — table rows, icons, and body text stay neutral.

**Explicit exception — rate-limit lockout message (D-05):** The "Too many attempts — try again in a few minutes." message must **not** use the destructive red. D-05 explicitly calls for a friendly, non-scary tone. Render it in a muted neutral tone — `#71717A` (zinc-500) body text, no red, no warning icon — to visually distinguish "you're just waiting" from "you did something wrong" (which the plain "Incorrect password." destructive-red message communicates instead).

## Surface Notes (Phase 1 specific)

These are implementation-guiding notes beyond the reusable design tokens above, mapping tokens to the six locked surfaces in scope.

1. **Login screen** — Centered card (max-width ~360px) on the dominant white background, using the secondary zinc-100 as the card surface to lift it visually. App name "TutorInvoice" (Heading, 20/600) above a single "Password" labeled input and "Unlock" button (accent blue, full-width on mobile). Error/lockout copy renders directly below the input, never as a toast/banner — keeps the whole interaction on one static screen with no layout shift surprises.

2. **Student roster (main page)** — Display-weight page title "Students" + "Add Student" button (accent) in the header row. Below: a shadcn `Table` on `md:` breakpoints and wider (columns: Name, Rate, Parent Email, Actions), alphabetically sorted (D-08). **Responsive default `[DEFAULT]`:** below the `md` breakpoint (<768px), render each student as a stacked card (name as Heading-ish emphasis, rate + parent email as Body lines, Edit/Archive actions as a button row) instead of a horizontally-scrolling table — chosen because the objective explicitly calls out phone use, and horizontally-scrolling tables are a common mobile usability failure for 3-column data.

3. **Empty state** — Occupies the same content region the table/cards would; centered, Heading "No students yet" + Body "Add your first student to get started." + a prominent centered "Add Student" button (accent), per D-15.

4. **Add/Edit modal dialog** — shadcn `Dialog`, stacked single-column fields (Name → Hourly Rate → Parent Email), each with a Label above and inline destructive-red error text below when invalid (D-16, blocks Save). Footer: Cancel (neutral) + Save (accent) buttons, right-aligned on desktop, full-width stacked on mobile (D-14 mobile-friendly).

5. **Archive flow** — Each roster row/card has an **"Archive"** action that ALWAYS renders a visible text label reading "Archive" — on BOTH the desktop table row and the mobile stacked-card layout, never icon-only (an accompanying icon is optional, but the text label is mandatory for accessibility). The action is neutral, not destructive-colored at rest — only the confirm dialog's action button is destructive-red, keeping the roster itself visually calm. Clicking opens the archive-confirm `Dialog` (D-12) described in the Copywriting Contract above.

6. **Archived view + restore** — `[DEFAULT — Claude's Discretion per CONTEXT.md]` A "Students" / "Archived" tab-link pair in the page header (accent-blue active-state underline/text) toggles between the two lists, matching RESEARCH.md's `/archived` route structure. The archived list reuses the same table/card layout and typography tokens, with a single-click "Restore" action per row (no confirm dialog — see Copywriting Contract) and its own empty state ("No archived students").
