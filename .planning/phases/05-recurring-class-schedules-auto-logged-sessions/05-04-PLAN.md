<threat_model>
ASVS L1 — client dialogs behind the login gate; all writes go through the Plan-02 server actions
(which own validation). No new server surface here.
- **Client-trusted values:** the form submits studentId/weekday/startTime/durationMinutes, all
  re-validated server-side by slotFormSchema (Plan 02) — the client dialog is not the security
  boundary; `noValidate` intentionally defers to server zod.
- **Accidental history loss (UX-security):** the remove flow requires an explicit confirm with
  copy stating logged sessions stay — prevents a mis-tap from being read as "delete history"
  (the actual delete never touches sessions, Plan 02).
- **XSS:** all rendered strings (student name, slot label) are React-escaped text nodes; no
  dangerouslySetInnerHTML. No new user-controlled HTML sink introduced.
- No secrets, no auth logic, no external calls in this plan.
</threat_model>
