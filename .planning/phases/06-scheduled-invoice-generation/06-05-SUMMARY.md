# Phase 6 Plan 05: Build the monthly invoice cadence cron job — Summary

**One-liner:** Monthly HWM cadence engine auto-generates invoices on/after the configured day, preventing double-billing via calendar-month high-water-mark, reusing the atomic helper and folding into the existing daily cron.

## Execution Overview

Plan 05 delivers RINV-02 requirement: on the daily cron, if auto-invoicing is enabled AND today (in the user's timezone) is on/after the cadence day AND this month has not already been invoiced, the cadence generates one invoice per student with unbilled sessions, then records the month as invoiced. This enables self-healing catch-up behavior (late/skipped Vercel Hobby run still fires the next day) while the monthly HWM guarantees at most one run per calendar month, preventing double-billing.

### Task 1: Create runInvoiceCadence — the monthly HWM cadence engine

**File:** `lib/invoice/cadence.ts`

Implements a new async function `runInvoiceCadence()` that returns `{ generated: number; skipped: number; ranThisMonth: boolean }`. The function follows the exact guard order from F5 research:

1. **Guard 1:** Load settings row (id=1). If `!invoiceCadenceEnabled`, return early with `ranThisMonth: false`.
2. **Guard 2:** Resolve timezone (`settings.timezone ?? DEFAULT_TIMEZONE`) and compute today's date in that zone via `todayInZone(tz)`. Extract month as `today.slice(0, 7)` ("YYYY-MM").
3. **Guard 3:** Check the HWM: if `lastInvoicedMonth === month`, return early. This is the self-healing mechanism — a late/skipped run still fires the next day but the HWM prevents duplicate runs within a single calendar month.
4. **Guard 4:** Resolve the effective cadence day:
   - Use `getDaysInMonth(new Date(\`${today}T00:00:00\`))` to compute the number of days in this month.
   - If `invoiceCadenceLastDay` is true, use the last day of the month; otherwise use `Math.min(invoiceCadenceDay ?? 1, daysInMonth)` to clamp a day-of-month to valid range.
5. **Guard 5:** Check if today's day-of-month is before the effective cadence day. If so, return early.
6. **Run:** Query `SELECT DISTINCT studentId FROM sessions WHERE billed = false`. For each student, call `generateInvoiceForStudent({ studentId, autoGenerated: true })` wrapped in try/catch. Increment `generated` on success, `skipped` otherwise; caught errors also increment `skipped` and continue (per-student try/catch ensures one failure never blocks the rest, mirroring Phase 5's `runAutoLog`).
7. **Guard 6:** After processing all students, update `settings.lastInvoicedMonth = month WHERE id = 1`. This advances the HWM so the next run won't fire until the next calendar month.
8. **Return:** `{ generated, skipped, ranThisMonth: true }`.

**Key design notes:**
- Uses `todayInZone(settings.timezone ?? DEFAULT_TIMEZONE)` throughout, never the server's UTC day, preventing off-by-one fires around UTC midnight.
- The double-billing guard from the atomic `generateInvoiceForStudent` helper (a per-student race guard via db.batch CTE) is the safety net if the monthly HWM is ever bypassed.
- Comments explain the HWM self-heal mechanism and the double-billing safety net.

## Key Design Decisions

1. **Reused atomic helper:** Both manual generation (Phase 03) and cadence auto-generation call the same `generateInvoiceForStudent({ studentId, autoGenerated: true })` helper, ensuring consistency and atomicity (double-billing guard via db.batch CTE).

2. **Monthly HWM over per-student tracking:** A single `lastInvoicedMonth` field on settings (vs. tracking per-student last-invoice dates) is simpler and sufficient — if a student had no unbilled sessions at cadence time, they don't need invoicing this month anyway. If they receive new sessions mid-month after the cron runs, those sessions are billed next month.

3. **Catch-up-once-per-month self-healing:** The combination of:
   - An early return if `lastInvoicedMonth === month` (HWM prevents duplicate runs)
   - A daily cron that fires at 8 AM UTC (imprecise on Vercel Hobby, may skip)
   - An early return only if today's day < effectiveDay (not if the cron missed a day)
   
   Ensures a late/skipped daily run still fires the next day (when today's day >= effectiveDay), but never fires twice in the same calendar month.

4. **No new auth/route/middleware:** Folding into the existing `/api/cron/auto-log` route reuses the `CRON_SECRET` bearer-token auth, the `force-dynamic` directive, and the `api/cron` middleware exemption. No new cron job added to `vercel.json` (Vercel Hobby caps cron count).

5. **Timezone-correct day resolution:** Always uses `todayInZone(settings.timezone)` to compute the calendar day, not the server/UTC day. This prevents the off-by-one fire-on-wrong-day edge case when server and user timezones differ around midnight UTC.
