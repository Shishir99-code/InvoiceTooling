# Phase 6 Research — Scheduled Invoice Generation

Answers "what do I need to know to PLAN this phase well?" Grounded in the live
codebase (not assumptions). Every reusable asset below was read directly.

## Decision-Critical Findings

### F1 — The DB driver is `neon-http`; reuse `db.batch`, NOT `db.transaction`
`lib/db/index.ts` wires Drizzle to `drizzle-orm/neon-http` (`neon(DATABASE_URL)`).

There is a **contradiction in the existing comments** worth flagging:
- `lib/actions/invoices.ts` (Phase 3) says the interactive `db.transaction()` API
  "throws at runtime on the neon-http driver" and uses a single **`db.batch`** CTE.
- `lib/schedule/auto-log.ts` (Phase 5) **does** use `db.transaction(async tx => …)`
  — and Phase 5 VERIFICATION passed with a live-tested cron. neon-http supports a
  *non-interactive* transaction (all statements known up front, no intermediate
  reads/branching), which is exactly how `runAutoLog` uses it.

**Resolution for Phase 6:** CONTEXT **D-04 is explicit** — the cadence loop reuses
"the same atomic single-`db.batch` CTE + double-billing guard" as
`generateInvoiceAction`. So we do **not** relitigate the primitive: extract the
Phase 3 `db.batch` CTE into a shared helper and call it per student. No new
`db.transaction` usage is introduced.

### F2 — `generateInvoiceAction` is the engine to factor out (RINV-02/RINV-03)
`lib/actions/invoices.ts:36-205`. The atomic core is one `db.batch([db.execute(sql\`
WITH target … ins … UPDATE sessions …\`)])` that:
1. Re-SELECTs unbilled sessions server-side (`billed = false`), ordered by date.
2. Freezes `periodStart/End`, `totalCents` (sum of stored `amountCents` — never
   re-derived from live rate), `lineItems` jsonb, `renderedBody`, `renderedSubject`.
3. INSERTs the invoice **gated on all target sessions still unbilled**
   (`WHERE (SELECT count(*) FROM target) = ${sessionIds.length}`) — the
   double-billing guard.
4. UPDATEs those sessions `billed = true, invoice_id = ins.id`.
5. Returns `invoice_id` or `null` (race lost → zero rows inserted).

The `INSERT INTO invoices (...)` column list is **hand-written SQL** (lines 150-157)
— adding `auto_generated` / `sent` columns means editing this SELECT literal, not
just the Drizzle schema.

**Extraction target:** a new `lib/invoice/generate.ts` exporting a pure-ish
`generateInvoiceForStudent(opts)` that both the Server Action (manual, returns the
email-draft pieces) and the cron loop (per student, ignores the draft) call.
Suggested shape:
```ts
type GenResult =
  | { ok: true; invoiceId: number; parentEmail: string; renderedSubject: string; renderedBody: string }
  | { ok: false; reason: "no-sessions" | "no-student" | "race-lost" | "error" };

async function generateInvoiceForStudent(opts: {
  studentId: number;
  autoGenerated: boolean;      // false = manual, true = cadence
  throughDate?: string | null; // RINV-03 cutoff; cadence always passes undefined
}): Promise<GenResult>;
```
`generateInvoiceAction` becomes a thin wrapper: zod-parse the form → call the
helper → map `reason` to the existing `fieldErrors` strings → build `emailDraft` →
`revalidatePath`. **Behavior of the manual path must not regress** (same error
copy, same `InvoiceActionState` shape).

### F3 — `runAutoLog` is the exact template for the cadence engine (RINV-02)
`lib/schedule/auto-log.ts`. The cadence job mirrors its discipline:
- Load one settings row (`id = 1`), resolve `tz = settingsRow.timezone ?? DEFAULT_TIMEZONE`.
- Compute "today" with `todayInZone(tz)` (`lib/schedule/time.ts`) — **never** the
  server/UTC day.
- **Per-item `try/catch` so one student's failure never blocks the rest** (D-04).
- Advance a durable **high-water-mark** after the run (D-03) — the monthly analog of
  `scheduleSlots.lastLoggedDate`.

New engine: `lib/invoice/cadence.ts` → `runInvoiceCadence(): Promise<{ generated: number; skipped: number; ranThisMonth: boolean }>`.

### F4 — Cron: FOLD into the existing daily route (Claude's discretion → decided)
`app/api/cron/auto-log/route.ts` is a `GET` that 401s via `isAuthorizedCronRequest`
(`lib/cron/auth.ts`, constant-time `CRON_SECRET` bearer, fails closed) then runs
`runAutoLog()`. `vercel.json` has **one** cron (`/api/cron/auto-log` @ `0 8 * * *`).

**Decision: fold, do not add a second cron.** Vercel Hobby caps cron count and
frequency (daily-only, imprecise, may skip — see [[vercel-hobby-cron-constraints]]).
The route runs **`runAutoLog()` first** (so any class scheduled for *today* exists
as a billable session) **then `runInvoiceCadence()`**, returning combined JSON.
`vercel.json` is unchanged; `middleware.ts` already exempts the whole `api/cron`
prefix; `CRON_SECRET` auth is reused as-is. **No new auth, route, or middleware.**

> Deploy note: Phase 5's cron already needs `CRON_SECRET` set in Vercel env
> ([[deploy-phase3-after-gap-fix]]). Phase 6 adds no new secret.

### F5 — Monthly HWM guard semantics (D-03)
Store `lastInvoicedMonth` as a `varchar(7)` `"YYYY-MM"` on `settings` (null = never
run). On each daily run:
```
if (!invoiceCadenceEnabled) return { ranThisMonth: false };   // toggle off
today = todayInZone(tz); month = today.slice(0,7);            // "YYYY-MM"
if (lastInvoicedMonth === month) return { ranThisMonth: false }; // already fired
effectiveDay = cadenceLastDay ? getDaysInMonth(...) : min(cadenceDay, getDaysInMonth(...));
if (Number(today.slice(8,10)) < effectiveDay) return { ranThisMonth: false }; // not yet
// → run generation loop for all students with unbilled sessions, then:
settings.lastInvoicedMonth = month;  // HWM: never fires twice this calendar month
```
This is **catch-up-once-per-month, self-healing**: a late/skipped daily run still
fires the next day (`today.day >= effectiveDay`), but the HWM guarantees at most one
run per calendar month. The double-billing CTE guard is the safety net if the guard
is ever bypassed.

`getDaysInMonth` (date-fns@4, confirmed present) computes the clamp for D-02. A
student whose generation throws is skipped for the month (per-student try/catch); the
month is still marked done (best-effort, matches "one bad row never blocks the rest").

### F6 — Two new `settings` columns + one for the day control (RINV-01, D-01/D-02)
Add to `settings` (`lib/db/schema.ts`):
- `invoiceCadenceEnabled boolean not null default false` — the on/off toggle.
- `invoiceCadenceDay integer` — day-of-month **1–28** (nullable; ignored when last-day on).
- `invoiceCadenceLastDay boolean not null default false` — explicit "last day of month"
  (D-02), avoids the ambiguous 29/30/31 range entirely.
- `lastInvoicedMonth varchar(7)` — the F5 HWM (nullable).

Recommend day range **1–28 + explicit "Last day"** over allowing 29/30/31, so the
only clamp path is the last-day option (cleaner UX, one code path).

### F7 — Two new `invoices` columns + backfill (RINV-04, D-07/D-08)
Add to `invoices` (`lib/db/schema.ts`):
- `autoGenerated boolean not null default false` — existing rows are manual → correct
  under the `default false` backfill.
- `sent boolean not null default false` — **but existing rows must backfill to `true`**
  (D-08: pre-feature manual invoices are already sent; don't flood the review queue).
  `drizzle-kit push` fills the column default (`false`) for existing rows, so the
  BLOCKING push task must ALSO run a **one-time backfill**:
  `UPDATE invoices SET sent = true;` (run once, immediately after push — every current
  invoice predates the feature). New inserts explicitly set `sent` (F8), so the
  `default false` is only ever seen by the (backfilled) existing rows.

Both new columns must be added to the hand-written CTE `INSERT INTO invoices (...)`
column list in the extracted helper (F2/F8).

### F8 — Sent-state write paths (RINV-04, D-08/D-09)
- **Cadence (auto):** helper inserts `auto_generated = true, sent = false`.
- **Manual generate:** helper inserts `auto_generated = false, sent = false`; the
  existing MAIL-05 draft-auto-open in `invoice-preview-dialog.tsx` fires
  `markInvoiceSentAction(id, true)` in its success effect (opening the draft = sent).
- **History "Email Invoice":** `invoice-view.tsx`'s Gmail anchor gets an `onClick` that
  optimistically calls `markInvoiceSentAction(id, true)` (D-09).
- **Undo:** a "Mark unsent" affordance calls `markInvoiceSentAction(id, false)` (D-09 —
  the app can't observe an actual send, so she can correct it).

New action `markInvoiceSentAction(invoiceId: number, sent: boolean)` in
`lib/actions/invoices.ts`: positive-int guard (mirror `deleteInvoiceAction`), single
`db.update(invoices).set({ sent }).where(eq(invoices.id, id))`, `revalidatePath("/history")`.

### F9 — History review-queue UI (RINV-04, D-07/D-08)
- `app/(app)/history/page.tsx` query adds `autoGenerated`, `sent` to the select.
- `components/invoice-history-table.tsx` `InvoiceHistoryRow` gains both fields; render

### F10 — Manual "bill through" cutoff (RINV-03, D-06)
- `lib/validation/invoice.ts`: extend `invoiceGenerateSchema` with an optional
  `throughDate` (`z.preprocess` blank→undefined, then `yyyy-MM-dd` string / `z.coerce.date`
  then reformat — keep it a string to match the `date` mode:"string" columns).
- `generateInvoiceForStudent` filters the unbilled re-SELECT with
  `and(eq(billed,false), lte(sessions.date, throughDate))` when a cutoff is present.
- `invoice-preview-dialog.tsx`: optional date `Input` (or the existing `calendar`/`popover`
  primitives); the client preview filters `sortedSessions` by the same cutoff so the
  frozen total the tutor sees matches what generates. **Cadence never sends a cutoff.**

## Pitfalls (carry forward from Phase 3/4/5)
1. **`db.transaction` is fine only non-interactively** on neon-http — but D-04 says
   reuse the `db.batch` CTE, so don't introduce transactions in the generation path.
2. **Never re-derive money** — sum stored `amountCents`; snapshots are immutable.
3. **`settings.timezone` drives the calendar day** — `todayInZone(tz)`, tz may be null
   → `DEFAULT_TIMEZONE`. Never `new Date().getDate()`.
4. **HWM idempotency, not row-existence** — re-running the daily cron must be a no-op
   after `lastInvoicedMonth` is set; don't guard on "does an invoice exist this month".
5. **Server sets `autoGenerated`/`sent`** — never trust a client-echoed value; they're
   written in the CTE / the mark-sent action only.
6. **FK discipline** — no schema FK changes; invoices/sessions FKs stay
   `restrict`/`set null`.
7. **`"use server"` files export only async functions**; `revalidatePath` after every
   mutation (`/history`, `/dashboard`, `/settings`).

## Validation Architecture (how each requirement is proven)
- **RINV-01:** Settings shows a toggle + day control; saving persists
  `invoiceCadenceEnabled` / `invoiceCadenceDay` / `invoiceCadenceLastDay`; reload
  reflects them.
- **RINV-02:** `curl` the cron route with the `CRON_SECRET` bearer on/after the cadence
  day → JSON reports `generated > 0`; a second immediate call reports `ranThisMonth:false`
  (HWM); a student with zero unbilled sessions gets no invoice; no session is double-billed
  (its `billed` stays true, one `invoice_id`).
- **RINV-03:** manual generate with a "through" cutoff excludes later-dated unbilled
  sessions from the frozen invoice; default (no cutoff) still bills all unbilled.
- **RINV-04:** auto invoices appear in History with "Auto" + "Not sent yet"; opening the
  draft flips them to sent (out of the queue); "Mark unsent" restores; nothing is ever
  auto-sent by the app.
- Cross-cutting: `tsc`, `lint`, `build` green; unauth cron → 401 (reused auth).
