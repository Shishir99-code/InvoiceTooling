<threat_model>
ASVS L1 — sent-state writes behind the password gate; "sent" is a best-effort local flag, not a delivery signal.
- **Authorization/integrity:** `markInvoiceSentAction` guards the id (positive integer) like
  `deleteInvoiceAction` and updates only the boolean `sent` for that id — it cannot mutate totals,
  snapshots, or another invoice. It runs behind the middleware login gate.
- **No delivery claim:** per PROJECT.md (client-side email only), "sent" is explicitly a local flag the
  tutor controls — the app makes no delivery guarantee; the reversible "Mark unsent" makes the
  best-effort nature safe (D-09).
- **Never auto-sends:** nothing in this plan (or the cadence) sends email; auto invoices start unsent and
  only her draft-open/toggle flips the flag — the send decision stays with her (RINV-04).
- **Optimistic UI:** the client updates state immediately but the server action + `revalidatePath` is the
  source of truth; a failed action leaves the server state unchanged (next load reflects reality).
- **No new external input beyond a boolean + id; no secret handling.**
</threat_model>
