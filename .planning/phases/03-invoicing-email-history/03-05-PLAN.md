<objective>
Close the one verified Phase 3 gap (03-VERIFICATION.md, Success Criterion 3 atomicity clause / 03-REVIEW.md WR-01): `generateInvoiceAction` currently inserts the invoice row and marks its sessions billed in TWO independent DB round-trips, so a mid-request crash or a two-tab race can leave sessions un-billed under a real invoice — allowing the same sessions (and money) to be billed twice.

This plan makes invoice generation atomic (single `db.batch`), adds a double-billing guard, and folds in two cheap same-file boundary-hardening fixes that protect the very same generate flow (WR-03 subject overflow) and the Settings write (WR-02 oversized input).

Purpose: Restore the atomicity invariant INV-03 requires — the core financial correctness guarantee for the app.
Output: Atomic `generateInvoiceAction`, a `text` `rendered_subject` column (migrated on Neon), and bounded Settings validation.

Explicitly OUT OF SCOPE (deferred, not gaps): WR-04 (generic try/catch + typed error state across all actions and their UI consumers — a broader robustness pass spanning UI components, not same-file hardening), and info items IN-01/IN-02/IN-03. Do NOT implement these here.
</objective>

  <action>
    Replace the two-round-trip write (the standalone INSERT...RETURNING at lines 122-133 AND the separate db.batch UPDATE at 135-145) with a SINGLE atomic write inside ONE `db.batch([...])` call.

    Use a single data-modifying CTE executed via `db.execute(sql\`...\`)` (import `sql` from drizzle-orm) placed inside the db.batch array, OR drizzle's `.with()` query-builder chain — either is acceptable as long as both writes land in one batch/transaction. The statement must:
    1. INSERT the invoice row (studentId, periodStart, periodEnd, totalCents, lineItems, renderedBody, renderedSubject) exactly as today, RETURNING its new id.
    2. In the SAME statement, UPDATE the covered sessions SET billed=true, invoiceId=<the new id>, targeting the unbilled session ids AND gated on `billed = false` (double-billing guard — never re-bill a session another generation already claimed).
    3. Gate the INSERT itself on all target sessions still being unbilled, so a concurrent second generation CANNOT persist an invoice covering already-billed sessions (e.g., INSERT ... SELECT ... WHERE the count of still-unbilled target sessions = the expected count). When zero rows are inserted (the race lost), return a fieldErrors state telling the user the sessions were already invoiced — retry.
    4. Return the new invoice id (via a trailing SELECT in the CTE or the batch result) so the action still returns `{ fieldErrors: null, invoiceId }` for the preview dialog's redirect to /history/{id}.

    PRESERVE unchanged: the zod parse + studentId boundary, the server-side re-SELECT of unbilled sessions (never trust client ids/total — T-03-04), the empty-set guard (line 58), the integer-cents `totalCents` reduce (never re-derive from live rate — D-14), the frozen renderedBody/renderedSubject/lineItems snapshot, and the two revalidatePath calls.

    Wrap the db.batch in try/catch: on a thrown DB error return a fieldErrors state (studentId: ["Couldn't generate the invoice — please try again."]) rather than letting it become an uncaught error page. (This narrow try/catch is scoped to THIS action's atomic write only — it is not the deferred broad WR-04 pass.)

    Do NOT reintroduce any INSERT that executes outside the batch. Do NOT use db.transaction() (throws at runtime on neon-http).
  </action>
