## Spacing Scale

Declared values (must be multiples of 4) — unchanged from Phase 1/2, no new scale introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, invoice line-item note indent (`pl-1` equivalent via 2 leading spaces in the text block itself, not a CSS class) |
| sm | 8px | Compact element spacing (`gap-2`: button pairs, form field labels) |
| md | 16px | Default element spacing (`gap-4`: form fields, card/dialog padding `p-4`) |
| lg | 24px | Section padding (`mb-6` heading-to-content gap) |
| xl | 32px | Layout gaps (page vertical padding `py-8`) |
| 2xl | 48px | Major section breaks (`py-12`) |
| 3xl | 64px | Page-level spacing (empty-state vertical padding `py-16`) |

**Exceptions:**
- **44px minimum tap target (`min-h-11`)** carried forward for the Dashboard row's
  clickable toggle zone — but see Surface 1 below: this phase **narrows** that
  clickable zone to the chevron+name segment only (not the full row), to make room
  for the new "Generate Invoice" sibling button without nesting `<button>` inside
  `<button>`. The overall row height stays `min-h-11` throughout.
- No other exceptions — Settings page, History table, and Invoice view reuse
  `student-table.tsx`'s exact `p-4` card / table cell paddings.

## Typography

Reused verbatim from the live Phase 1/2 codebase — no new sizes introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / small / error | 14px (`text-sm`) | 500 (`font-medium`, shadcn `Label` default) for labels; 400 for help/error text | 1.0 for labels; 1.5 for help/error text |
| Body | 16px (`text-base`) | 400 (regular) | 1.5 |
| Heading | 20px (`text-xl`) | 600 (`font-semibold`) | 1.2 (`leading-tight`) |
| Display | 28px (`text-[28px]`) | 600 (`font-semibold`) | 1.2 (`leading-tight`) — page `<h1>` only |
| Invoice text block (new, this phase) | 14px (`text-sm`) | 400 (regular) | 1.6 (`leading-relaxed`, slightly looser than body for a document-like block) — `font-mono` (Geist Mono) |

**Weight note (2-weight content rule, unchanged):** All new Phase 3 copy uses
exactly two weights — **regular 400** and **semibold 600** — identical to Phase
1/2. **Medium 500** remains reserved for shadcn primitive internals only (`Button`,
`Label`, `TableHead`, `DialogTitle`) — do not introduce `font-medium` in new
page-level/custom copy, including the invoice text block (which stays `font-mono`
+ regular weight throughout, even for the header line — no bolding inside the
frozen invoice text, since it must render identically whether viewed in-app,
copied to a plain-text clipboard, or pasted into an email body with no markdown
support).

## Color

Reused verbatim from the live Phase 1/2 codebase. **Same duality carried forward:**
shadcn's own primitives use the oklch CSS-variable tokens in `app/globals.css`
(`--primary`, `--muted`, `--destructive`), while page-level custom code hardcodes
literal Tailwind `blue-600`/`red-600`/`zinc-*` classes. Phase 3 follows this
**exact same duality** — do not switch page-level accents to the oklch tokens.

**No second semantic color is introduced.** Settings' save-success confirmation
(see Copywriting Contract) is rendered in neutral `zinc-600`, not a new green —
avoids adding a semantic hue this app has never needed before.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` / `oklch(1 0 0)` (`bg-background`, `bg-white`) | Page background, dialog/table/invoice-block container fills |
| Secondary (30%) | `zinc-50`–`zinc-200` (`#fafafa`–`#e4e4e7`), white cards with `border-zinc-200` | Table containers, mobile stacked cards, nav bar bottom border, dialog footer (`bg-muted/50`), **the invoice text block's background (`bg-zinc-50`)** — treats the frozen invoice as a distinct "document" surface within the page |
| Accent (10%) | `#2563eb` (Tailwind `blue-600`) | Reserved for: "Save Settings" primary button, "Generate & Freeze" confirm button, "Email Invoice" primary button, the active top-nav tab (text + 2px bottom border, now 5 items — see Surface 1). **Never** applied to the "Generate Invoice" trigger on the Dashboard (that stays `outline`, per the "trigger buttons are neutral, only the confirming action is colored" precedent — see Surface 1), never to plain body text, borders, or decoration. |
| Destructive | `#dc2626` (Tailwind `red-600`) | Reserved for: the "Delete Invoice" **confirm** button inside its dialog only (the trigger button on the invoice view stays `outline`, matching `SessionDeleteConfirmDialog`'s exact precedent — trigger neutral, confirm red), inline field-validation error text (`text-red-600`). |

Accent reserved for exactly: **"Save Settings," "Generate & Freeze," "Email
Invoice," and the active top-nav item** — the four primary/affirmative actions
this phase introduces, plus nav state. Every other new button (Generate Invoice
trigger, Copy Invoice Text, Delete Invoice trigger, View [invoice] in History,
Cancel/Keep Invoice) is `outline` — never accent, never destructive-colored until
inside its own confirm step.

## Data Formatting Conventions

*(Addendum beyond the base template — required for the new invoice text block,
merge-field rendering, and History list; extends Phase 2's table with Phase
3-specific formats.)*

| Value | Format | Example | Rationale |
|-------|--------|---------|-----------|
| Money | `formatCents(cents)` (unchanged, `lib/format.ts`) | `$375.00` | Same single source of truth used for invoice line amounts and totals — never re-implemented |
| Duration | `formatDuration(minutes)` (unchanged, `lib/format.ts`) | `1 hr 30 min` | Same helper used for invoice line-item durations |
| Line-item date | `date-fns format(date, "PPP")` (unchanged from Sessions/Dashboard) | `July 3, 2026` | Consistency over abbreviation — the invoice should read like the rest of the app, not a compressed ledger format |
| Period label (D-03) | Single session: `format(date, "PPP")`. Multiple sessions: `` `${format(min, "PPP")} – ${format(max, "PPP")}` `` (en dash, spaces both sides) | `July 3, 2026` or `July 3, 2026 – July 17, 2026` | Matches D-03's exact example format; single-date collapse resolves the "Claude's Discretion" edge case explicitly |
| Invoice line item | `` `${dateLabel} · ${durationLabel} · ${amountLabel}` ``, then — **only if the session has a note** — a second line indented two spaces: `  {note}` | `July 3, 2026 · 1 hr 30 min · $112.50`⏎`  Reviewed chapter 4 quiz` | Per D-01; blank/absent notes omit the second line entirely (no empty indent, no placeholder dash) |
| Invoice header (inside the `{invoice}` merge field) | `` `Tutoring Invoice — ${studentName}` `` on its own line, then the period label, then a blank line before line items | `Tutoring Invoice — Alex Kim`⏎`July 3, 2026 – July 17, 2026` | Per D-05 — no business name/branding, no invoice number (D-04) |
| Invoice total (inside `{invoice}`) | `` `Total: ${formatCents(totalCents)}` `` on its own line, preceded by a blank line after the last line item | `Total: $375.00` | Single trailing summary line, no subtotal/tax rows (out of scope) |
| Merge fields | `{invoice}`, `{student}`, `{total}`, `{zelle}`, `{period}` — sequential `String.replaceAll` per 03-RESEARCH.md Pattern 3, unknown tokens left verbatim (no throw, no silent strip) | `{invoice}` → the full block above | Per D-12/D-13 — gives the tutor an obvious visual cue (a literal `{stuent}`) if she mistypes a field, rather than silently disappearing text |
| Generated date (History list + Invoice view) | `date-fns format(generatedAt, "PPP")` | `July 5, 2026` | Consistent with every other date display in the app — no time-of-day shown (not needed at this app's scale) |

## Surface Specifications

*(Addendum beyond the base template — the 5 phase surfaces named in the
orchestrator prompt each get an explicit, unambiguous contract here so the
executor has no open design questions.)*

### 1. Top nav — add Settings + History (Claude's Discretion, resolved)

- **Five flat items, in this order:** Students · Dashboard · Sessions · History ·
  Settings. Rationale: History is a data view (like Dashboard/Sessions) so it sits
  with its peers; Settings is app configuration, so it sits last — same ordering
  logic as most CRUD apps' "config always last" convention.
- **No new nav pattern.** Same visual style, same active-state treatment
  (`text-blue-600 border-b-2 border-blue-600` active / `text-zinc-600
  hover:text-zinc-900` inactive) as the existing 3-item `components/top-nav.tsx`.
  Archived students remain a nested Students sub-tab (Phase 1 D-02) — unaffected.
- **Mobile:** unchanged precedent from Phase 2's UI-SPEC — no hamburger/drawer for
  5 items; if the row overflows on the narrowest viewports, allow
  `overflow-x-auto` horizontal scroll rather than building a collapsed-menu
  pattern (still a single-user app; over-engineering avoided).
- `NAV_ITEMS` array in `components/top-nav.tsx` gains two entries:
  `{ href: "/history", label: "History" }` and
  `{ href: "/settings", label: "Settings" }`.

### 2. Dashboard row — "Generate Invoice" trigger (D-06, D-08)

**DOM restructure required** (flagged explicitly since it changes existing,
already-shipped code in `dashboard-table.tsx`): the row header is currently a
single full-width `<button>` covering chevron + name + duration + amount. A
`<button>` cannot contain another `<button>`, so the "Generate Invoice" trigger
must sit as a **sibling**, not nested inside the existing toggle.

- New structure: an outer `flex min-h-11 w-full items-center gap-2 px-4 py-2`
  wrapper `<div>` (replacing the outer `<button>`) containing:
  1. An inner `<button type="button" className="flex flex-1 items-center gap-2
     text-left">` — the accordion toggle, now covering **only** the chevron +
     student name (narrower click zone than before; still `min-h-11` tall via
     the parent).
  2. A `<span className="flex items-center gap-4">` — duration + amount, plain
     (no longer part of the clickable toggle zone; this is an accepted
     trade-off to make room for the sibling button below).
  3. **`Generate Invoice`** button (`variant="outline"`, `size="sm"`) —
     **omitted entirely** (not rendered) when `row.unbilledAmountCents === 0`
     (D-08 resolved: hidden).
- Clicking "Generate Invoice" opens the preview modal (Surface 3) for that
  student — does **not** expand/collapse the row.
- The row's existing expand/collapse behavior (showing unbilled sessions,
  Edit-only actions per Phase 2 D-13) is otherwise unchanged.

### 3. Generate-invoice preview modal (D-07)

Clones `components/ui/dialog.tsx`'s shell (same `Dialog`/`DialogContent`/
`DialogHeader`/`DialogFooter`, same `useActionState` pattern as
`SessionFormDialog`) — a new `invoice-preview-dialog.tsx`.

- **Title:** "Generate Invoice for {student}" (see Copywriting Contract).
- **Description:** the irreversibility warning (see Copywriting Contract),
  rendered via `DialogDescription` (`text-sm text-muted-foreground`).
- **Body:** the **fully-rendered email text** (subject + body, merge fields
  resolved against the *live* Settings row and the *live* unbilled sessions for
  this student) — not just the itemized block — so the tutor sees precisely what
  will be frozen, including her own greeting/closing prose. Rendered as:
  - Subject line, `text-sm font-semibold` (one of the two allowed weights),
    prefixed with a small `text-zinc-600` "Subject:" label.
  - A `gap-2` vertical space, then the body in a bordered block:
    `rounded-lg border border-zinc-200 bg-zinc-50 p-4 font-mono text-sm
    whitespace-pre-wrap leading-relaxed text-zinc-900` — this exact treatment
    (mono, zinc-50, bordered) is reused verbatim for the Finished-invoice view
    (Surface 4) and History's open-invoice view, since it is the same frozen
    text in both places.
- This preview is computed **client-side from data already available** (the
  `sessionsByStudentId` prop already passed into `DashboardTable`, plus a
  Settings read passed down from the Dashboard Server Component) — a
  non-authoritative preview only, exactly mirroring the Log Session modal's "≈
  $X.XX" precedent (Phase 2 Surface 2). The Server Action independently
  re-fetches unbilled sessions and the Settings row at generate time and is the
  sole source of truth for what actually gets frozen (03-RESEARCH.md Pitfall 1 /
  Anti-Patterns).
- **Footer:** "Cancel" (outline, closes without writing) + "Generate & Freeze"
  (accent, submits `generateInvoiceAction`).
- On success: dialog closes and the app **navigates to the finished invoice**
  (Surface 4) — not a bounce back to the Dashboard (D-09).

### 4. Finished-invoice view (D-09, D-15) — shared by post-generate landing and History "open"

One component (`invoice-view.tsx`), one route pattern
(recommend `/history/[id]` for both the post-generate landing redirect and
History's "View" action — planner may confirm the exact path, but the UI
contract requires it be the **same page/component** in both cases per D-15, not
two separate views that could drift).

- **Heading:** `<h1>` **"Invoice — {student}"** (28px/600, matches every other
  page's `<h1>` treatment).
- **Metadata line** directly under the heading: `text-sm text-zinc-600` —
  **"{period} · Generated {generatedAt} · {total}"** — e.g. "July 3, 2026 – July
  17, 2026 · Generated July 17, 2026 · $375.00".
- **Rendered text block:** the exact frozen `renderedSubject` + `renderedBody`
  (never re-derived from live `sessions`/Settings — 03-RESEARCH.md Pitfall 4),
  same visual treatment as the preview modal's body block (mono, `bg-zinc-50`,
  bordered, `whitespace-pre-wrap`). Subject shown first as a labeled line
  ("Subject: {renderedSubject}"), then the body block below.
- **Action row** (single `flex gap-2` row, no special separation — mirrors
  `StudentTable`'s Edit+Archive grouping precedent):
  1. **"Email Invoice"** (accent) — `<a target="_blank" rel="noopener
     noreferrer" href={gmailComposeUrl}>` styled as a `Button`. **Omitted**
     (see Copywriting Contract's over-length guard) when the encoded URL
     exceeds ~1,800 characters; the warning line renders in its place.
  2. **"Copy Invoice Text"** (outline) — always present (D-11), copies the
     frozen `renderedBody` (body only, not the subject — matches how a parent
     would paste it into an existing email's body field) via
     `navigator.clipboard.writeText`. Label swaps to "Copied!" for ~2s on
     success; on failure, reveals the auto-selected fallback `<textarea>` (see
     Copywriting Contract).
  3. **"Delete Invoice"** (outline trigger) — opens the delete-confirm dialog.
     **Only entry point for delete** (not duplicated on the History row) —
     keeps a single destructive entry point per invoice, mirroring Phase 2's
     "Dashboard = Edit only, Sessions page = Edit+Delete" single-entry-point
     precedent.
- Deleting successfully navigates back to `/history` (the list).

### 5. Invoice History (D-14) + Delete confirm (D-16)

- Route: `app/(app)/history/page.tsx`. Heading: `<h1>` "Invoice History" (nav
  label stays "History" — see Surface 1).
- **Flat, newest-first** (`orderBy(desc(invoices.generatedAt))`), no grouping/
  filtering (D-14 — simplest scan, explicitly not grouped-by-student).
- Reuses `StudentTable`'s exact responsive **table (md+) / stacked cards
  (mobile)** pattern — **not** the accordion pattern from Dashboard/Sessions
  (History rows do not expand in place; they navigate to the Invoice view).
- **Columns:** Student | Period | Total | Generated | Actions (right-aligned,
  a single outline "View" button/`Link` to `/history/{id}`).
- **Mobile card:** student name (bold, `font-medium`) + "View" button on the
  first line (`justify-between`, matches `StudentTable`'s card header), then
  period / total / generated as three `text-base text-zinc-600` lines below
  — identical layout rhythm to `StudentTable`'s and `SessionTable`'s mobile
  cards.
- **Empty state** (zero invoices generated yet): full `py-16` centered layout,
  identical structure to `StudentTable`'s/`SessionTable`'s empty state — see
  Copywriting Contract for heading/body/action.
- **Delete-invoice confirm dialog** (`invoice-delete-confirm-dialog.tsx`):
  clones `SessionDeleteConfirmDialog`/`ArchiveConfirmDialog` exactly (same
  `Dialog` shell, same bound-Server-Action-on-submit pattern via
  `deleteInvoiceAction.bind(null, invoiceId)`). Triggered **only** from the
  Invoice view (Surface 4), never from the History row directly. Copy per the
  Copywriting Contract's delete-invoice rows.

### 6. Settings page (SET-01, SET-02)

New page, not a modal (unlike every other form in this app so far) — settings
are a standalone destination, not an item-scoped add/edit action.

- Route: `app/(app)/settings/page.tsx`. Heading: `<h1>` "Settings" (28px/600).
- **Field order (top to bottom), each with a `Label` + optional helper text +
  input, identical field-block spacing (`flex flex-col gap-2`) to
  `SessionFormDialog`'s fields:**
  1. **Zelle Handle** — Label "Zelle Handle". Helper (`text-sm text-zinc-600`):
     "Email or phone number parents will Zelle payment to." `Input` (shadcn,
     `type="text"`, not `type="email"` — it may hold a phone number), placeholder
     `"you@example.com or (555) 123-4567"`. Validation: non-empty after trim
     only (SET-01's loose validation, Claude's Discretion resolved) — see
     Copywriting Contract for the error message.
  2. **Email Subject** — Label "Email Subject". Helper: "Supports {student},
     {total}, {zelle}, {period}." `Input`, defaultValue from the existing
     Settings row or the shipped default: **"Tutoring Invoice for {student}"**.
  3. **Email Body** — Label "Email Body". Helper: "Supports {invoice},
     {student}, {total}, {zelle}, {period}. {invoice} inserts the itemized
     session list and total." `Textarea` (shadcn), `rows={10}` (taller than the
     3-row Notes textarea elsewhere, since this is the page's primary content),
     defaultValue from the existing Settings row or the shipped default:
     ```
     Hi there,

     Here's the invoice for {student}'s tutoring sessions ({period}):

     {invoice}

     You can send payment via Zelle to {zelle}. Thank you!
     ```
- **Footer:** single **"Save Settings"** button (accent), no "Discard"/Cancel
  (this is a persistent settings page, not a transient add/edit flow — there is
  nothing to discard back to). On success, "Saved." appears inline beside the
  button for ~2s (see Copywriting Contract — no new semantic color).
- `noValidate` on the form; server-side zod is the sole validation gate,
  matching every other form in this app.

### 7. Notes-are-parent-facing hint (D-02)

- In `SessionFormDialog` (both `add` and `edit` modes — the same shared
  component), insert one line between the existing "Notes (optional)" `Label`
  and the `Textarea`:
  `<p className="text-sm text-zinc-600">Notes appear on invoices sent to
  parents.</p>`
- No other change to the Notes field — it stays optional, same placeholder,
  same 3-row `Textarea`. This is a labeling-only addition (D-02 — no schema
  change).
